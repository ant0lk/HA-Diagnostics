# Диагностический ZIP

Версия продукта: `1.0.0-alpha.6`. Основной сценарий: владелец открывает дополнение через Home Assistant Ingress, нажимает «Собрать ZIP-архив», видит прогресс и скачивает готовый файл. Никакая настройка MCP, OAuth, ChatGPT или Tunnel для этого не требуется.

## Умный дом Яндекса

В панели откройте блок **«Умный дом Яндекса»**, введите OAuth-токен с правом **чтения устройств `iot:view`**, включите «Собирать историю Яндекса» и сохраните подключение. Зарегистрировать своё OAuth-приложение и получить токен можно по [инструкции Яндекса](https://yandex.ru/dev/dialogs/smart-home/doc/ru/concepts/platform-protocol). Право `iot:control` сборщику не требуется. Токен вводится только в панели установленного дополнения; повторно он не показывается. При изменении интервала/срока оставьте поле пустым, чтобы сохранить действующий токен. Изменения действуют без перезапуска. Выключение сбора сохраняет накопленную историю в пределах выбранного срока.

Сборщик в ZIP-worker получает полный список устройств через фиксированный `GET https://api.iot.yandex.net/v1.0/user/info`, затем доступность каждого через `GET /v1.0/devices/{device_id}`. [Ответ устройства](https://yandex.ru/dev/dialogs/smart-home/doc/ru/concepts/platform-device-info) содержит отдельное поле `state=online/offline`; выключенная лампа или розетка при этом может быть онлайн. Данные об умениях, сценариях, комнатах и присутствии людей не сохраняются. Управляющие запросы, произвольные URL, перенаправления и внешние прокси запрещены. В режиме MCP этот сборщик не запускается. В демонстрационном режиме реальное подключение Яндекса отключено.

По умолчанию опрос идёт **раз в 60 секунд**, хранение — **30 дней**. В панели доступны 30–3600 секунд и 1–365 дней. Интервал отсчитывается после завершения цикла; медленные ответы и ограничения API увеличивают фактическое расстояние между наблюдениями. При ошибках включается задержка повторов до часа; для 429 учитывается `Retry-After` в пределах 60–3600 секунд. Одновременно допускаются четыре запроса, таймаут сетевых операций 10 секунд и 120 секунд на весь цикл. Поддерживается до 1000 устройств: превышение не выдаётся за полный список и не означает удаления устройств. Дополнение должно быть запущено, панель можно закрыть. Сбор ZIP не инициирует сетевой опрос: в архив попадает единая копия накопленных наблюдений.

В приватной SQLite-базе хранятся только очищенные метаданные и история доступности. `session_id` разделяет подключения, `device_ref` — устойчивый псевдоним устройства; одинаковые псевдонимы связывают список и события. Названия заменяются псевдонимами. Токен хранится отдельно в приватном файле с правами 0600 на Linux и не включается в ZIP, ответы панели или ошибки. Существующая очистка также удаляет известный токен Яндекса из других источников ZIP, если он встречается в диагностике настроек/логах HA. Приватный каталог исключён из HA backup и поставки.

Одинаковые последовательные статусы сжимаются: `observed_at` — начало наблюдаемого отрезка, `last_observed_at` — последняя проверка, подтвердившая состояние. `previous_observed_at`, `previous_status` и `change_window` дают границы обнаруженного изменения. Точный момент перехода неизвестен; короткие изменения между опросами могут быть пропущены. Это доступность по данным облака Яндекса, а не прямое измерение устройства в LAN. История до подключения не восстанавливается. При замене токена создаётся новая сессия, чтобы не объединить два разных аккаунта; старые записи остаются в пределах срока хранения.

Ошибки сети, авторизации, HTTP 404 и неизвестный ответ создают `unknown` с кодом причины, а не `offline`. Перезапуск и длительная задержка опроса отмечают перерыв; `resumed` означает возобновление наблюдения и не доказывает непрерывность прежнего статуса. `removed` записывается только после успешного чтения полного списка, в котором ранее добавленного устройства больше нет. Возврат устройства и изменение названия сохраняют его `device_ref`. Устаревший текущий статус отображается как отсутствие свежего наблюдения. При обратном переводе часов новые записи приостанавливаются до восстановления временного порядка, с кодом `YANDEX_CLOCK_INVALID`.

В ZIP прикладывается **весь сохранённый интервал Яндекса**, независимо от 24-часового окна Recorder. На границе срока хранения исходное время старого отрезка обрезается, `started_before_retention` показывает такую границу. Защитные пределы — 30 000 отрезков истории и 5000 общих пропусков; вытеснение сверх них отмечается счётчиком `storage_evictions`. Пропуски отдельного устройства видны в его истории как `unknown`; общие сбои чтения списка/перерывы — также в `coverage.gaps`. При неподключённом источнике `coverage.json` сообщает `configured=false`, без ложной ошибки; список/история добавляются после подключения либо при наличии ранее сохранённых записей. Недоступная/повреждённая база Яндекса отмечается в manifest и не останавливает другие источники HA.

Локальные проверки используют имитацию API и часов. Реальное чтение Яндекса с вашим токеном, ограничения облака на большом аккаунте, работа после перезапуска HA OS и скачивание через Ingress требуют проверки на установленном дополнении.

## Новые источники Alpha 5

WebSocket использует фиксированные чтения реестров, `repairs/list_issues`, `persistent_notification/get`, `system_log/list`, `system_health/info`, `trace/list`, `trace/get`, `recorder/list_statistic_ids`, `recorder/validate_statistics`, `recorder/statistics_during_period`. Управляющие команды и произвольные параметры запрещены в коде. System Health читается до `finish`, с применением `initial`/`update`, проверкой ID и общим пределом 32 MiB / 90 секунд; разрыв после initial сохраняет полученное с `partial`.

Контракты сверены с [traces Core 2026.9.4](https://github.com/home-assistant/core/blob/2026.9.4/homeassistant/components/trace/websocket_api.py), [System Health](https://github.com/home-assistant/core/blob/2026.9.4/homeassistant/components/system_health/__init__.py), [Recorder](https://github.com/home-assistant/core/blob/2026.9.4/homeassistant/components/recorder/websocket_api.py) и [Supervisor API](https://developers.home-assistant.io/docs/api/supervisor/endpoints/). Диагностика устройств использует GET `/core/api/diagnostics/config_entry/<entry_id>/device/<device_id>` для ID из registry; отсутствие поддержки/прав/API отмечается в manifest.

Сохраняются до 200 последних доступных трасс каждого домена и до 128 пар диагностики устройств. Покрытие трасс не считается полным за сутки. Статистика: до 64 ID, сначала накопительные (`has_sum`), затем остальные по ID; интервал строго 7 дней, шаг день. Метаданные/проблемы читаются отдельно, selection показывает выбранные/пропущенные ряды; достижение предела даёт `partial`.

Ресурсы хоста берутся только из `/proc/cpuinfo` и `/proc/meminfo` (до 1 MiB): модели CPU, логические процессоры, общая/доступная память, swap. `/sys/fs/cgroup/memory.max` и `cpu.max` показывают лимиты контейнера отдельно. В VM это ресурсы гостя. Неизвестные характеристики не выводятся из лимита памяти Core; отсутствующие файлы отмечаются. Дополнительных прав host PID/DBus/full access не требуется. Для диска читается только `default`, без удалённых mounts.

Сравнение берёт последний готовый сохранённый ZIP того же режима demo/live до начала текущего сбора, включая Alpha 4. Конфигурация сопоставляется по исходному пути, реестры сортируются перед сравнением. Текущие состояния, нагрузка, логи, версии доступных обновлений и скрытые секреты не сравниваются. Недоступное чтение не считается удалением; известно только окно между наблюдениями. После смены ключа обезличивания сравнение Alpha 5 недоступно. Первый архив содержит `no_previous_archive`. Повреждение предыдущего ZIP или предел 4 MiB/файл, 32 MiB суммарно не останавливает остальные чтения.

`coverage_details` показывает время первых/последних и минимальных/максимальных распознанных записанных строк, строки без времени и использование пояса HA для локальных timestamps. При неизвестном поясе время не угадывается. При обрезке записываются полученные/сохранённые байты, строки, причина и последний timestamp. Пустая история не доказывает отсутствие события. Фоновая подписка на события и накопление нагрузки в Alpha 5 не включены.

## Конфигурация

Alpha 5 следует `use_blueprint.path` в `blueprints/automation`/`blueprints/script`, `filename` YAML-панелей и буквальным Jinja `from`/`import`/`include`/`extends` в `custom_templates/*.jinja`, включая вложенные импорты. `dependencies` связывает документы. Макросы сохраняются текстом внутри очищенного JSON, `!input` — структурной ссылкой; шаблоны не исполняются. Динамический импорт даёт `CONFIG_DYNAMIC_REFERENCE`. Сохраняются прежние ограничения путей, symlink/hardlink, секретных/скрытых каталогов и расширений. Неиспользуемые blueprints/макросы не сканируются.

Live-профиль использует readonly map `homeassistant_config` в `/homeassistant`. Это стандартный механизм [конфигурации приложений Home Assistant](https://developers.home-assistant.io/docs/apps/configuration/). Основные сведения HA остаются в `home_assistant/config.json` и `system/`: версии, компоненты, единицы, часовой пояс, состояние, аппаратура и сеть. `configuration/index.json` связывает их с сохранёнными настройками и реестрами.

YAML читается начиная с `configuration.yaml`, а также существующих `automations.yaml`, `scripts.yaml`, `scenes.yaml`, `customize.yaml`, `ui-lovelace.yaml`. Поддерживаются относительные `!include`, `!include_dir_list`, `!include_dir_named`, `!include_dir_merge_list`, `!include_dir_merge_named`, включая вложенные файлы и packages. В ZIP каждый документ записывается отдельно в JSON с `source_path`; include и YAML merge остаются структурными ссылками, объединённая конфигурация не вычисляется. `!secret` и `!env_var` сохраняются как скрытые ссылки без чтения значений; Jinja не исполняется. Неизвестные теги помечаются и их payload скрывается. Исходные комментарии YAML не включаются.

Конечный список `.storage`: `core.config_entries`, `core.config`, `lovelace`, `lovelace_dashboards`, `input_boolean`, `input_number`, `input_select`, `input_text`, `input_datetime`, `counter`, `timer`, `schedule`, `zone`, `person`. Дополнительные `lovelace.<id>` выбираются только по проверенным ID из списка dashboards. Несуществующие необязательные хранилища пропускаются; отсутствующий основной YAML, core.config_entries, недоступные права и повреждённые файлы отражаются в index/manifest. Права файлов HA не меняются.

Параметры интеграций читаются из сохранённого [core.config_entries](https://github.com/home-assistant/core/blob/dev/homeassistant/config_entries.py), поэтому не зависят от поддержки diagnostics конкретной интеграцией. Загруженное состояние интеграции нужно сопоставлять с `registries/integrations.json`: несохранённые изменения и настройки, ещё не применённые после редактирования YAML, могут отличаться.

Настройки дополнений берутся тем же GET `/addons/<slug>/info`, без повторного запроса и без управляющих операций. [Supervisor API](https://developers.home-assistant.io/docs/api/supervisor/endpoints/) возвращает options для роли manager/admin; пустой словарь может означать отсутствие опций либо их скрытие upstream, полнота в этом случае не утверждается. `data_path` и другие несекретные пути внутри options сохраняются. Приватные каталоги дополнений, их собственные файлы конфигурации, внешние include, auth-хранилища и произвольные `.storage` не читаются; это покрытие настроек HA и Supervisor, не побайтовый backup всех приложений.

## Все доступные логи

Экспорт использует конечные GET-чтения журналов с `Range: entries=:0:18446744073709551615`, начиная с самой старой доступной записи. Стандартный предел последних 100 строк и прежний предел 50 000 строк не применяются. Endpoint без `/latest` или фильтра загрузки запрашивает весь сохранённый журнал источника, включая доступные прошлые загрузки.

API и формат Range сверены с [официальной документацией Supervisor](https://developers.home-assistant.io/docs/api/supervisor/endpoints/) и [реализацией LogsControl](https://github.com/home-assistant/supervisor/blob/main/supervisor/host/logs.py). История и события читаются через [REST API Home Assistant](https://developers.home-assistant.io/docs/api/rest/). Диагностика интеграций — через [Core diagnostics API](https://github.com/home-assistant/core/blob/dev/homeassistant/components/diagnostics/__init__.py).

Удалённые журналы и уже очищенная история не восстанавливаются. Отсутствие Recorder / Logbook / diagnostics, отказ в доступе, ошибка или разрыв соединения записываются как `unavailable` / `partial` с фиксированным кодом причины. Сбор остальных источников продолжается. Завершённое чтение не доказывает полноту исторических данных: в manifest отдельно указаны неизвестные retention/exclusions.

## Очистка и доступ

Исходные данные проходят очистку в отдельном credential worker до записи в ZIP. Логи обрабатываются потоком, включая многострочные PEM-блоки; полный журнал не загружается в память. Токен Supervisor не передаётся процессу интерфейса, MCP или транспорту. UI обращается к конечным IPC-командам; peer UID проверяется ядром Linux. Все обращения к HA — GET или фиксированные команды чтения WebSocket. Управление устройствами, перезапуск или изменения конфигурации отсутствуют.

Распознаваемые секреты, credentials, пароли, ключи и конфигурационные поля типа password в Supervisor schema скрываются до записи. В разделе configuration несекретные options и описание схемы сохраняются, включая вложенные структуры; в прежних информационных JSON options/schema остаются скрытыми. Имена, entity ID, адреса, MAC и email очищаются/псевдонимизируются существующим локальным Redactor. Нативные registry ID сохраняются для связи записей. Сырые файлы HA, `secrets.yaml`, auth-хранилища, база Recorder, медиа и приватные файлы самого дополнения не копируются. Неизвестный секрет может не распознаться: перед передачей файла следует просмотреть содержимое.

Скачивание проверяет ту же подтверждённую Ingress-сессию владельца, что и панель. POST-команды дополнительно защищены CSRF. Файл выбирается только по проверенному ID архива в фиксированном каталоге; путь от клиента не принимается. ZIP скачивается потоком, без чтения целиком в память. Каталог экспорта доступен credential worker и UI, но не query worker.

## Ежедневное автосохранение

Расписание включено по умолчанию: **03:00 каждый день по часовому поясу Home Assistant**. В панели «Ежедневный автоархив» можно изменить время с точностью до минуты или выключить автосохранение, затем нажать «Сохранить расписание». Изменения действуют без перезапуска. Часовой пояс считывается фиксированным GET-чтением `home_assistant/config`; он показан рядом с временем, а дата следующего сбора и списки архивов отображаются в этом поясе. До первого получения пояса автосбор ждёт; при временной недоступности HA используется последнее сохранённое значение.

Планировщик работает в export worker и не зависит от открытой панели. Дополнение должно быть запущено. Проверка наступления времени выполняется каждые 30 секунд; если уже идёт ручной сбор, автоматический ждёт его завершения. После простоя создаётся только сегодняшний пропущенный архив, без сбора за предыдущие дни. Настройки и отметка запуска атомарно сохраняются в приватном каталоге дополнения. Изменение времени, повторное включение и удаление готового ZIP не создают второй автоархив за уже обработанную дату. Прерванный остановкой дополнения незавершённый автосбор можно повторить после запуска; готовый ZIP повторно не создаётся.

Недостаток диска или недоступность источника до старта не расходуют дневной запуск: планировщик повторяет попытку. Явная отмена владельцем или ошибка уже начатой сборки завершают сегодняшнюю попытку; кнопка ручного сбора остаётся доступна. При переходе на летнее время отсутствующий час сдвигается вперёд на величину пропуска; при повторе часа выбирается первое вхождение, с одним запуском за локальную дату.

`manifest.json` включает `kind` (`automatic` / `manual`), `scheduled_date`, `archive_filename` и метаданные `ARCHIVE_STRUCTURE.txt` с размером и SHA-256. Дерево строится из реально записанных ZIP entries: отсутствующие JSON-источники в него не добавляются, частичные лог-файлы перечисляются. Причины пропусков остаются в manifest.

## Хранение и пределы

Сохраняются отдельно последние **7 готовых автоматических** и **3 готовых ручных** архива. Срок в 24 часа больше не применяется; старейший ZIP соответствующего вида удаляется после готовности нового архива сверх лимита. Ошибка или отмена не вытесняют готовые файлы. Завершённые архивы и настройки расписания доступны после перезапуска. ZIP Alpha 2 без типа сбора распознаётся как ручной. Отмена удаляет недописанный ZIP. Собранные архивы исключены из HA backup.

Пределы защиты дополнения: 128 MiB входящих / очищенных данных на источник, 512 MiB очищенных данных на весь набор (служебные manifest, README и файл структуры отдельно), 32 MiB на JSON-ответ, 1 MiB на строку лога, минимум 100 MiB свободного диска, до 5 минут на источник логов и до 90 секунд на JSON-чтение. При достижении предела manifest указывает причину; архив не выдаётся как полный. Это конечный диагностический экспорт. Включённая история доступности Яндекса накапливается отдельно, с собственным сроком хранения и пределами.

Для сохранённой конфигурации дополнительно действуют: 4 MiB на файл, по 32 MiB суммарных входящих данных и развёрнутой JSON-структуры, 256 попыток чтения файлов/ссылок, глубина 64, 100 000 узлов YAML, 8 Mi символов после раскрытия YAML aliases и 4096 элементов на include-directory scan. Symlink/junction, hardlink, абсолютные и выходящие за корень include, secrets-файлы и non-YAML include отклоняются. Ошибки parser/доступа/лимитов дают безопасные коды `CONFIG_*` и не останавливают сбор остальных источников.

## Проверка и совместимость

Локальная демонстрация: `python -m ha_diagnostics.runtime --demo --data .local-data --web web`. Демо не обращается к HA и явно помечает архив тестовым. Тесты `tests/test_zip_export.py` проверяют состав ZIP, более 50 000 строк, 24 часовых окна каждого вида истории, очистку, SHA-256, частичные источники, лимиты, отмену, восстановление скачивания и запрет неавторизованного доступа. `tests/test_export_schedule.py` проверяет расписание, местную дату HA, сохранение настроек, раздельное хранение 7/3, восстановление, защиту изменения настроек и полноту дерева ZIP.

После изменения исходников копии в `ha_diagnostics_live/app/src` и `app/web` должны совпадать с основными. Slug `ha_diagnostics_live` сохранён; версия продукта — `1.0.0-alpha.6`. Старые компоненты MCP и локальные настройки сохранены; для прежнего режима нужен явный `--workflow mcp` / `HAD_WORKFLOW=mcp`. В ZIP-режиме они не запускаются.

`tests/test_configuration_export.py` проверяет YAML с include/packages, интеграции, помощники и dashboards, исходные пути и index, сохранение значений, очистку secret-typed addon options, недоступный mount, ограниченные пути/объёмы, опасные YAML tags, циклы/глубину/duplicate keys и запрет чтения конфигурации в import-only. Исходные файлы после сборки сравниваются по SHA-256.

`tests/test_alpha5_export.py` проверяет новые источники и конечный allowlist, события initial/update/finish System Health, сохранение частичных результатов, выбор трасс/device diagnostics/statistics, паспорт хоста, сетевой контекст, зависимости конфигурации, покрытие логов и сравнение архивов, включая Alpha 4, смену ключа и повреждённый baseline. Локальные результаты сохранены в `docs/verification/alpha5-local-checks.json` и `alpha5-pytest.xml`.

На реальной HA OS ещё нужно проверить: установку/обновление, readonly mount и права чтения `/homeassistant` для UID export worker, Ingress ID владельца, Linux UID/IPC, доступность конкретных API и скачивание большого ZIP через HA Ingress. Локальные fixtures подтверждают кодовый контракт, а не эти live-проверки.
